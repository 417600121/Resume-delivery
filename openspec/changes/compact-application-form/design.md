## Context

参见 `proposal.md` 的问题说明。当前 `RecordModal.vue` 将岗位信息、投递上下文和跟进记录按三个纵向区段排列，并使用带有 `max-height` 和整体 `overflow: auto` 的通用弹窗样式。现有字段、历史建议、条件来源说明和保存逻辑已可用，限制主要来自布局层级、文本域高度和弹窗滚动边界。

## Goals / Non-Goals

**Goals:**

- 在 `1024×768` 及以上的桌面窗口中，让新增投递的完整录入流、关闭和提交操作一次可见。
- 用紧凑而仍可扫描的字段网格替代纵向堆叠的大段分组说明，保持字段含义清晰。
- 将长文本的增长限制在输入框内部，避免其挤出表单底部操作区。
- 保持 `RecordModal` 的数据草稿、校验、建议、条件字段和事件接口不变。

**Non-Goals:**

- 不修改投递记录的数据模型、本地存储、状态时间线、导入导出或保存事件语义。
- 不把新增投递改为独立路由、分步向导或标签页流程。
- 不新增移动端断点、移动端布局或移动设备验收范围。
- 不改变其他弹窗的尺寸或滚动策略，除非共享样式会直接影响新增投递表单。

## Decisions

### 1. 为新增投递表单使用专用的紧凑桌面网格

为 `RecordModal` 增加专用的样式标识，并将字段组织为桌面优先的多列网格：公司和职位占据主要宽度，地点、优先级、来源、状态和下一步使用较短列；招聘信息与备注各占稳定的较宽区域。分组标题改为低高度的区段标记或字段集标题，不再保留占用大量垂直空间的说明段落和编号。

选择专用网格而非继续调整通用 `.form`，是为了避免影响状态时间线、选项和其他弹窗中的既有布局。备选方案是继续使用纵向分组并固定底部操作区，但它只能让保存按钮始终可见，不能满足全部字段无需滚动的目标。

### 2. 固定弹窗结构，并禁止表单整体滚动

新增投递弹窗采用标题区、表单工作区和操作区的稳定三段结构；在目标桌面视口中通过受控宽度、紧凑间距和字段高度使其自然落入可视高度。该弹窗的内容区域不再使用整体纵向滚动，关闭、取消和保存始终保留在工作面内。

不采用折叠区段、标签页或“更多字段”抽屉，因为这些方案虽然减少了初始高度，却隐藏了用户录入时需要比较和补充的字段，并增加额外点击。

### 3. 将长文本溢出限制为文本域内部行为

招聘信息和备注文本域使用固定的可视行数，并禁用会改变外层高度的垂直拖拽；输入内容超出空间时使用文本域自身的纵向滚动。文本域仍保留完整编辑能力和已有 Markdown 输入语义。

备选方案是允许文本域自适应增长或拖拽扩展。该方案会破坏单屏高度保证，因此不采用；内部滚动是长文本与高效单屏录入之间的明确取舍。

### 4. 复用现有数据与交互逻辑，并覆盖编辑场景的视觉回归

只调整模板结构和样式层，保留 `draft` 初始化、`submit`、必填属性、`HistoryInput`、条件来源字段和 `close`/`save` 事件。新增与编辑共用同一组件，因此实现后编辑模式会使用相同的紧凑结构；验收重点仍是新增投递流程及其数据兼容性。

不创建第二个“新增投递”组件，以免两套字段定义、默认值和校验逻辑在后续维护中分叉。

## Risks / Trade-offs

- [风险] `1024×768` 桌面窗口中的列宽较紧，较长的字段标签或历史建议可能影响可读性。→ 使用最小列宽、可截断但不丢失语义的辅助文本，并在目标窗口逐项检查控件与标签不重叠。
- [风险] 固定高度文本域减少了长内容的同时可见行数。→ 仅将滚动限制在对应文本域内，并保留清晰标签、内部滚动和完整保存能力。
- [风险] 现有 CSS 中的通用弹窗和响应式规则可能覆盖专用布局。→ 以新增投递专用选择器限定规则，检查现有媒体查询不会在目标桌面宽度改写网格或恢复整体滚动。
- [风险] 浏览器缩放、系统较大字体或低于目标的窗口可能超出单屏设计边界。→ 明确验收基准为默认缩放下不小于 `1024×768` 的桌面窗口；本变更不承诺移动端或更小窗口布局。

## Migration Plan

1. 盘点 `RecordModal` 的字段、默认值、条件显示和事件，确认只调整展示结构。
2. 为新增投递表单实施专用网格、固定文本域与无整体滚动的弹窗样式。
3. 在 `1024×768` 和 `1280×800` 桌面窗口中验证普通来源、其他来源和长文本录入；同时回归保存、取消、必填校验和编辑模式。
4. 运行生产构建与变更规格校验。若需要回滚，只撤销 `RecordModal.vue` 和相关样式调整，不需要迁移或清理用户数据。
